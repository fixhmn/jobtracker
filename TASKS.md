# JobTracker — задачи реализации

Отмечены задачи, реализованные и проверенные локально. Диалоги и доставка Telegram проверяются с тестовыми ответами; подключение настоящего бота, Docker-запуск, несколько дней использования и публичная публикация ещё не проверены.

Код worker, Docker Compose, CI, backup и README уже подготовлен. JT-03/JT-16 требуют токен владельца; JT-23 требует запуск workflow на GitHub; JT-24/JT-25 требуют Docker Engine; JT-26/JT-27/JT-29/JT-30 требуют практической проверки и публикации. Локальный backup/restore проверен тестом.

## Этап 1. Подготовка

- [x] **JT-01 — создать окружение и структуру.** Подготовить app, bot, worker, tests; выбрать поддерживаемую версию Python, описать зависимости и воспроизводимую установку. Готово: окружение устанавливается по инструкции на чистой машине, импорты работают.
- [x] **JT-02 — конфигурация и секреты.** Добавить настройки, `.env.example` и `.gitignore`. Готово: недостающий обязательный параметр вызывает понятную ошибку; токены, БД, логи и реальные данные не попадают в Git.
- [ ] **JT-03 — создать Telegram-бота.** Получить токен через BotFather, определить свой Telegram ID. Готово: бот отвечает владельцу на /start; чужому ID не выдаёт данные и не разрешает действия. Проверять авторизацию также для callback-кнопок.

## Этап 2. Backend и база

- [x] **JT-04 — каркас FastAPI.** Реализовать health, конфигурацию логов и проверку API key. Готово: health доступен; рабочие маршруты без правильного ключа возвращают 401; секреты не логируются.
- [x] **JT-05 — схема SQLite.** Создать applications, status_history, reminders; foreign keys и индексы. Предусмотреть версионируемую инициализацию схемы. Готово: повторный запуск не удаляет данные; неверная ссылка на application не создаётся.
- [x] **JT-06 — создание вакансий.** POST /applications, валидация полей и зарплаты, нормализация URL, проверка дубликатов. Готово: корректная запись даёт 201; дубликат — 409; ошибочные данные — 422; запросы параметризованы.
- [x] **JT-07 — список и карточка.** GET списка и отдельной записи, фильтры, поиск, limit/offset. Готово: стабильный порядок, ограниченный размер страницы, 404 для неизвестного ID.
- [x] **JT-08 — редактирование и статусы.** PATCH, applied_at и история. Готово: изменение статуса и запись истории атомарны; повтор статуса не создаёт событие; исправление ошибочного статуса разрешено и видно в истории.

**Контрольная точка:** через /docs можно добавить вакансию, найти её и изменить статус. После перезапуска данные сохраняются.

## Этап 3. Telegram-интерфейс

- [x] **JT-09 — API-клиент бота.** Асинхронные HTTP-запросы с таймаутами и обработкой ошибок. Готово: при падении backend бот не зависает и объясняет проблему; 409/404/422 отображаются понятными сообщениями.
- [x] **JT-10 — /new и /cancel.** Пошаговый ввод company, position, url, необязательных полей и подтверждение перед сохранением. Готово: можно отменить ввод, пропустить зарплату, исправить ошибочную ссылку; отмена не создаёт запись.
- [x] **JT-11 — список и карточка.** /list, /view, пагинация и кнопки статуса. Готово: пользователь добавляет вакансию и отмечает Applied без ручного обращения к API; ID выбранной записи не теряется между шагами.
- [x] **JT-12 — справка и корректный текст.** /help, обработка неизвестных команд и экранирование пользовательского ввода. Готово: названия с символами форматирования не ломают сообщение; пользователь знает, как отменить текущий диалог.

**Контрольная точка:** начать пользоваться ботом для своих откликов. Пока без автоматических напоминаний.

## Этап 4. Напоминания

- [x] **JT-13 — CRUD напоминаний.** Создание, список, complete и cancel. Готово: напоминание связано с существующей вакансией; sent и completed различаются; повторное complete безопасно.
- [x] **JT-14 — время Остина.** Преобразование America/Chicago ↔ UTC, /remind и /today. Готово: границы местного дня корректны; проверить обычную дату, смену DST и просроченное напоминание.
- [x] **JT-15 — выдача worker через claim/lease.** Атомарное получение наступивших записей. Готово: два одновременных claim не получают одну активную запись; после истечения lease зависшее напоминание снова доступно.
- [ ] **JT-16 — worker и Telegram-доставка.** Отдельный процесс, graceful shutdown, фиксация результата, лимит повторов и backoff. Готово: напоминание приходит в нужный чат, успешная доставка фиксируется, временный сбой повторяется, постоянный виден как failed.
- [x] **JT-17 — управление из бота.** /done и кнопки выполнения/отмены. Готово: отменённые и выполненные записи не отправляются; /today показывает невыполненные, включая уже доставленные.

**Контрольная точка MVP:** создать вакансию → отметить Applied → назначить ближайшее напоминание → получить его → отметить выполнение. Повторить после перезапуска компонентов.

## Этап 5. Статистика

- [x] **JT-18 — SQL-статистика.** GET /stats с from/to, текущие статусы и уникальные переходы. Готово: повторное возвращение в Interview не завышает число интервью; период имеет чёткие границы.
- [x] **JT-19 — /stats в боте.** Отчёт за 30 дней и понятные подписи. Готово: пустая база не вызывает ошибку; история и текущие статусы не смешиваются; нет вводящей в заблуждение «конверсии».

## Этап 6. Проверки качества

Добавлять тесты вместе с реализацией соответствующих этапов; этот этап закрывает сквозные сценарии.

- [x] **JT-20 — тесты API и БД.** Отдельная временная БД для каждого тестового сценария. Покрыть авторизацию, валидацию, дубликаты, фильтры, историю, applied_at и 404. Готово: тесты не меняют личную БД и проходят независимо от порядка запуска.
- [x] **JT-21 — тесты worker и времени.** Mock Telegram и управляемые часы; проверить success, retry, failed, lease recovery, DST, cancelled/completed. Готово: тесты не ждут реальное время и не отправляют настоящие сообщения.
- [x] **JT-22 — сквозной smoke-сценарий.** Проверить add → Applied → reminder → delivered → completed в локальном окружении. Готово: сценарий воспроизводится по инструкции; результат можно показать в демонстрации.
- [ ] **JT-23 — CI.** GitHub Actions: установка зависимостей, тесты, выбранный линтер/форматтер. Готово: корректный commit проходит, намеренно сломанный тест останавливает проверку; реальные секреты не нужны.

## Этап 7. Docker и повседневное использование

- [ ] **JT-24 — контейнеры.** Dockerfile и compose с api, bot, worker. Healthcheck API и обработка ожидания его готовности. Готово: запуск по инструкции; API опубликован на localhost; БД доступна только API.
- [ ] **JT-25 — persistence и резервная копия.** Volume SQLite, безопасная процедура backup/restore. Готово: down/up не теряет записи; тестовая копия восстанавливается; процедура не сводится к копированию только основного файла работающей WAL-базы.
- [ ] **JT-26 — практическая проверка.** Несколько дней пользоваться продуктом на собственных откликах. Готово: найденные ошибки исправлены, личная БД остаётся вне репозитория. Период использования записывается фактически, без выдуманных показателей.

## Этап 8. GitHub и портфолио

- [ ] **JT-27 — README и пример данных.** Problem, features, setup, commands, env, API examples, tests, ограничения. Добавить синтетический demo dataset отдельной командой; не автоматически в личную БД. Готово: другой человек запускает проект по README без помощи автора.
- [x] **JT-28 — архитектура и решения.** Описать зачем FastAPI, SQLite и отдельный worker; границы единственного пользователя, lease, возможность дублей после аварии, дальнейшее масштабирование. Готово: объяснение соответствует реализованному коду.
- [ ] **JT-29 — демонстрация.** Скриншоты /docs и Telegram; короткое видео add → status → reminder. Готово: демоданные, без токенов, настоящих контактов и откликов.
- [ ] **JT-30 — публикация и резюме.** Проверить содержимое и историю Git на секреты; выбрать лицензию; публиковать только проектную папку. Публичную загрузку выполнять по отдельному запросу владельца. Готово: CI проходит, ссылка на репозиторий работает, resume bullets описывают только завершённые функции и реальные даты.

## Порядок и ориентир по времени

1. Окружение и API: этапы 1–2.
2. Реальный пользовательский сценарий: этап 3.
3. Напоминания: этап 4 — основной законченный MVP.
4. Статистика, тесты и CI: этапы 5–6.
5. Docker, личное использование и GitHub: этапы 7–8.

Ориентир — 2–4 недели неполной занятости при знакомстве со стеком; это план, не обещание срока. Сначала довести один сквозной сценарий до рабочего состояния, затем расширять.
